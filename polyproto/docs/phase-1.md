# Phase 1 -- Name the memory boundary in types

Implementation plan for Phase 1 of [`owned-and-observed.md`](owned-and-observed.md): introduce an
ownership predicate, route the scheduler's ledger reads through one narrow interface, and publish
the count of call sites that assume *allocation* authority over engine-owned state.

**Status: implemented and measured.** `Tier` is in [`tier.rs`](../src/tier.rs); the predicate is
[`own.rs`](../src/own.rs); the `Telemetry` boundary is [`tele.rs`](../src/tele.rs); the
authority-split entry points and the `census` feature are in
[`cache.rs`](../src/cache.rs) and [`Cargo.toml`](../Cargo.toml); `polyphonic ownership` prints the
table and both census numbers. Byte-identity holds on every command in §5's reproducible set,
checked before and after each of the four work items in §4 individually, not just once at the end.
§2's four predictions are annotated below with what was actually found.

This is the *memory* boundary. §2's path boundary is Phases 0 and 8 and shares nothing with it --
no file, no type, no constant -- so the two chains can be worked in either order or at once.

Phase 1 changes no result. That is the deliverable: **byte-identical output on every seeded
subcommand**, plus a number that says how large Phase 3 is. The number is generated by the compiler
rather than estimated, because an estimate of how much code assumes a disclaimed authority is
exactly the kind of guess this phase exists to replace.

**Why a type and not a comment.** §8 already tabulates what Phase 3 touches and calls
`machine.rs`'s share "moderate, mechanical". Nothing in the repository tests that. The claim rests
on `accelerated()` locating the work -- and §8 also says `accelerated()` is a **tier** predicate,
not an ownership one, and that §1's table cuts across it twice. So the estimate is built on a
predicate that is known to be the wrong predicate. Writing the right one down is cheap, and its
first output is a work list.

## 1. What has to be settled before the type is written

§9 says the obvious shape is wrong and names the two rows that break it. It does not say what the
right shape is. Five things have to be settled first; three of them changed the design while this
was written.

### 1.1 `Ownership` keyed on `BlobKind` fails because a partition is not a kind

The natural first move is `fn owner(kind: BlobKind) -> Ownership`. It gives `KvBlock -> Engine`,
which reads correctly and loses the thing Phase 3 is actually built on: **the orchestrator sizes
the HBM partition the engine allocates within**. A partition has no `BlobKind`. It is a property of
a *pool*, and a function whose only argument is a class has nowhere to put it.

The same failure in the other direction: `offloaded KV in host DDR` is engine-allocated while
sitting inside a budget the orchestrator owns. Keyed on kind alone, `KvBlock -> Engine` says the
orchestrator has no say over host DDR, which would delete §1's third save (targeted intra-host DDR
arbitration) and with it the mechanism behind the surviving soft-floors result.

Both rows are recovered by the same axis, and it is not the tier -- it is **which question is
asked**. Capacity authority and allocation authority have different answers for the same class in
the same pool. That is §1's two-tier control system stated as a signature rather than as prose.

### 1.2 The tier axis is load-bearing for capacity and, today, constant for allocation

Having added the question axis, the tier axis needs its own defence, because the table it produces
is not what §9's phrasing suggests.

- **Capacity.** The question is *of a pool*: HBM's capacity is the partition the orchestrator
  granted, DDR's is the host budget, NVMe's is the spill file. Asking it without naming a tier is
  incoherent, so the tier axis is the whole question here.
- **Allocation.** Every cell today is a function of the class alone: `KvBlock` and `WeightShard`
  are the engine's in whichever tier they sit, `Snapshot` and `ServiceHeap` are the orchestrator's.
  The tier column is constant.

So the honest statement is that **the tier axis does not currently discriminate on the allocation
question**, and P1 below predicts it. Keeping the axis anyway is a deliberate choice with two
reasons, and it is worth recording which is load-bearing.

The weak reason is symmetry. The strong one is that the cells that are *about* to differ are named:
Phase 3 splits the HBM pool, after which `authority(KvBlock, Hbm, Capacity)` still answers
`Orchestrator` but refers to a partition rather than to a `Quota` floor; Phase 6 unfreezes partition
sizing and makes per-tenant partitions a decision, which is a capacity answer that starts depending
on more than the tier. A signature that dropped `kind` from the capacity question -- which today's
table would justify -- has to be widened again at Phase 6, and widening a signature is how a
two-line table edit becomes a refactor. **The table is meant to be edited; the signature is not.**

### 1.3 NVMe under an accelerated class is a judgement call, made explicitly

`cache.rs` demotes HBM evictions into DDR and DDR evictions onto NVMe, so a `KvBlock` can reach the
spill tier. §1's table stops at host DDR and says ownership there *follows the connector*. Extending
that rule gives `authority(KvBlock, Nvme, Allocation) = Engine`, since a connector's disk tier
(`LMCache`'s, in the stack being modelled) is the thing that pool represents.

The alternative -- `Orchestrator`, on the grounds that the spill file is the ledger's own artifact
and no engine knows it exists -- is defensible and would make the tier axis discriminate on the
allocation question immediately, which is a tempting reason to prefer it and a bad one.

Chosen: **Engine**, following the connector, because the rule is §1's and inventing a second rule to
make a prediction come out interesting is the failure mode §7 is about. What it would change if
wrong: NVMe-resident KV becomes orchestrator-allocated, `Hierarchy::spill` stays owned through Phase
3, and the census shrinks by the sites that touch the spill tier for accelerated classes. Named here
so the decision is visible if a later phase wants to revisit it.

### 1.4 "Route every ledger access through it" cannot mean every access

`machine.rs` reads residency in two distinguishable ways, and collapsing them would break Phase 4
rather than prepare for it.

- **Belief reads**, for deciding: `believes_resident`, `believes_held`, the residency prefix in
  `plan`, `could_admit` and `displacement` at the placement sites. These are what `Telemetry` must
  mediate. Under `Control::Unified` and `Control::Query` they return the truth today, which is why
  this phase is a no-op and why Phase 4 has somewhere to put a belief.
- **Truth reads**, for executing: `apply_chain` and `apply_deps` ask `self.domains[p].holds(...)`
  *after* the plan is made, on purpose -- "the plan was made against the scheduler's view; the peer
  is asked against the truth" -- and that is what makes a stale view cost something instead of
  silently succeeding.

Routing the second group through `Telemetry` would make a stale view free and quietly delete the
`stale_fetches` counter's meaning. So Phase 1 names them instead: the two truth reads get an
explicit accessor (`ground_truth_holds`) whose doc comment says why it is not a telemetry read.
**The gap between those two accessors is what §3.6's divergence metric measures**, so Phase 4 gets
its subtraction already localised rather than having to find it.

### 1.5 The census has to be split by authority before it can be counted

§9 asks for "a count of call sites assuming *allocation* authority over engine state", generated by
the compiler. The obvious mechanism -- mark `TierPool::admit` and count the warnings -- **over-counts
by every `Snapshot` and `ServiceHeap` admission**, which are allocations the orchestrator genuinely
owns and Phase 3 does not touch. A count that includes them is not a feasibility answer, it is a
count of how often the ledger admits anything.

So the entry points have to be split by authority first:

```rust
fn admit_owned(&mut self, id: BlobId, meta: BlobMeta) -> Admission
fn admit_engine(&mut self, id: BlobId, meta: BlobMeta) -> Admission
```

with today's `admit_hot` becoming a dispatcher that consults `authority(...)` and forwards. Only
`admit_engine` and its siblings carry the census marker. The split is not census scaffolding to be
removed afterwards -- it *is* the Phase 3 seam: Phase 3 replaces `admit_engine`'s body with the
engine cache model and leaves `admit_owned` alone.

### 1.6 `Quota` is the other thing Phase 3 deletes, and nothing currently says so

§8's "what gets easier" says the engine cache is simpler than a `TierPool`: LRU over block hashes,
no quotas, bands, floors or refusal. The consequence runs the other way and is not written down
anywhere: **per-class floors, bands and limits over engine-allocated classes in HBM stop being
representable**, because a class-blind LRU cannot honour a per-class floor. `Quota.floor[KvBlock]`
and `Quota.limit[WeightShard]` in the HBM pool are dead on Phase 3's arrival, and
`arms.rs::Budget::accelerator` exists to compute exactly those entries.

That is a second, independent work list, and it is invisible unless asked for. Phase 1 asks for it
by giving `Quota`'s per-class accessors the same treatment as the allocation entry points, so the
census reports two numbers rather than one.

## 2. Predictions, stated first

§7's rule. Four predictions, each attached to a claim it would rewrite.

**P1 -- capacity authority is the orchestrator's in all twelve (kind, tier) cells.** §1's "the loss
is granularity, not authority" says so, and §1's table has no counterexample: the orchestrator sizes
the partition, owns the DDR quota, and owns the spill file.

- *If right:* the uniformity is a result worth printing rather than an assumption, and the two-tier
  control system is exactly two tiers -- one question answered one way everywhere, one answered per
  class.
- *If wrong* (some cell is `Engine`): Phase 3's partition-level admission check is not authoritative
  even in principle, §1's bound-versus-utilisation tradeoff loses the half that was supposed to stay
  a real check, and Phase 3's admission sweep is measuring something weaker than it claims.

**Measured: confirmed.** `own::tests::capacity_authority_is_uniformly_orchestrator` asserts it over
every `(BlobKind, Tier)` pair, and §4.2's table has `Orchestrator` in every capacity cell by
inspection. The two-tier control system is exactly two tiers.

**P2 -- the allocation census is 10-25 static sites, and `machine.rs`'s share of it is at most 5.**
From reading the call graph: the bulk sits in `cache.rs` (`admit_hot`'s four callers, `demote`,
`spill`, `forget_cold`, `anticipate` at two sites in `announce`, `touch` at four, `remove`,
`drain_all`), with `machine.rs` contributing the `could_admit` filter in `place_agent`, the
`displacement` term in `placement_terms`, and the residency prefix in `plan`.

- *If right:* §8's "moderate, mechanical" for `machine.rs` holds, and the correction is concentrated
  in the file §8 already says carries "the bulk of it".
- *If wrong* on the low side (under 10): either the split in §1.5 is too coarse to be informative,
  or the ledger is less entangled than §8 fears and Phase 3 is smaller than budgeted.
- *If wrong* on the high side (`machine.rs` above 5): the scheduler, not the ledger, is where the
  disclaimed authority lives, and Phase 3's risk profile changes -- the file that has to be rewritten
  is the one holding the placement score every published result depends on.

**Measured: wrong on the low side, and the mechanism explains why rather than just the ledger's
shape.** The static census is **12**, not 10-25, and `machine.rs`'s share is **0**, not "at most 5".

The first number is mostly an artifact of what the lint can count, set out in §4.4: `#[deprecated]`
fires once per *named item*, so each authority-split entry point contributes exactly one warning
however many callers route through its dispatcher. P2 was written expecting call-site granularity
-- "`admit_hot`'s four callers" -- which the mechanism cannot deliver; those four collapse to the
one line inside `admit_hot` that names `admit_engine`. §6's risk 3 anticipated the shape of this
("a count of *sites*, not of *decisions*") without noticing it also invalidated P2's units. The
twelve are `Hierarchy::{admit,anticipate,touch,demote,forget_cold,drop_superseded,spill_displaced,
drain}_engine` and `Quota::{floor,limit,band}_of_engine` plus `Quota::set_band_engine`.

**`machine.rs`'s zero is not an artifact, and it is the more interesting half of the miss.**
`machine.rs` never calls `TierPool::admit` or its siblings; every read it makes of `Hierarchy` goes
through `is_hot`/`holds` (now `Telemetry::resident`/`held`, or `ground_truth_holds` on the
execution path), `local_ns`, `displacement`, `could_admit` -- residency and cost *queries*, not
allocation *decisions*. Phase 1's belief/allocation split (§1.4) and its authority split (§1.5)
turn out to be the same line: nothing in `machine.rs` was ever deciding allocation, so nothing there
was ever going to be census-marked. §8's "moderate, mechanical" survives, but for a sharper reason
than "the correction is concentrated in `cache.rs`" -- `machine.rs` has no allocation authority to
disclaim in the first place.

**The dynamic census is the number P2 was reaching for.** `polyphonic ownership` on its default
15,000-op trace: 347,916 engine-authority operations on `KvBlock` and 48,239 on `WeightShard`, zero
on both owned classes. By entry point, `admit` 93,921, `demote` 86,753, `spill` 86,753,
`superseded` 59,904, `anticipate` 13,100, `touch` 5,011, `forget_cold` 2,474.

That distribution is itself a Phase 3 finding, and not the one the first draft of this section
reported. **Admission is under a third of it.** Demotion matches admission one for one, the cascade
spill matches it again, and superseded-copy removal is two-thirds of it -- so an engine-cache model
that replaces admission and leaves the offload and promote paths alone covers well under half of
what this ledger does on the engine's behalf. The first version of this census counted only
`admit_engine` and reported 20,143 for `KvBlock`; the second counted five entry points and reported
201,259; this one counts twelve. Each correction moved the number by more than the previous total,
which is the honest reason to distrust a census that has not been checked against the call graph
rather than assembled from the entry points someone happened to split.

**P3 -- `accelerated()`'s seven call sites survive the split as tier questions, with at most one
turning out to be an ownership question in disguise.** §8 warns that the predicate conflates two
concepts. Reading the sites, all seven look like genuine tier questions: `Quota::offloaded` demotes
offload copies' band, `Budget::accelerator` moves a split's share onto the classes that live in HBM,
`on_accelerator` and `hot_ids` resolve which pool a class is usable from, `rpcbench` reports.

- *If right:* the conflation §8 names is **latent, not realised** -- the value of the type is
  prospective, and Phase 1 fixes no bug. Worth saying plainly rather than implying the refactor
  repaired something.
- *If wrong* (several are ownership questions): §8's "the useful half survives" is true in a stronger
  sense than claimed -- `accelerated()` was already doing ownership's job and doing it wrong -- and at
  least one published result rests on a predicate answering a question it was not asked.

**Measured: confirmed, and by inspection rather than by argument.** None of the seven call sites
changed: `Quota::offloaded`, `Budget::accelerator`'s two sites, `on_accelerator`'s replacement
(`tier_of(kind) == Tier::Hbm`), `hot_ids`, and `rpcbench`'s report all kept their exact bodies.
`tier_of` -- the one place §1.1's real ownership axis lives now -- is new code, not a repurposing of
`accelerated()`. The conflation §8 warned about stayed latent, as predicted.

**P4 -- byte-identity holds on every seeded subcommand.** The refactor moves no arithmetic. The one
plausible failure is iteration order: `refresh_view` collects `hot_ids()` into a `HashSet`, and
`hot_ids` chains two `HashMap` iterations whose order the refactor could perturb.

- *If right:* it is what "no-op by construction" is supposed to mean, and Phase 3's re-measurement
  has a clean base to diff against.
- *If wrong:* **the finding is worth more than the refactor.** A published number that moves when
  `HashMap` iteration order changes is a published number with an undeclared input, and §7 says
  provenance is part of the number. Do not repair it quietly -- report which result moved and by how
  much, then decide whether the order-dependence is a defect or a seed.

**Measured: confirmed, checked incrementally rather than once at the end.** `residency`, `flows`,
`placement` (split and unified memory) and `volatility`, each at a reduced `--ops` and at a second
seed, `diff`ed byte-for-byte after every one of §4's four work items landed -- not only after the
last one, so a break would have been caught at the item that caused it rather than blamed on
whichever landed most recently. `distributed`, `code-review` and `data-path` (which cannot be
byte-identical at all, per §5's correction) were smoke-run after each item too, and produced the
same node/served/refused counts and arm labels throughout. As added bonus of the incremental checks,
§5's own error was itself found this way: the first capture attempt included those three commands
in the byte-identity set, and running the baseline capture twice against itself -- before touching
any code -- showed they disagree with themselves. That is P4's method working correctly one level
up, on the test rather than on the refactor.

## 3. What the type must and must not do

Four rules, so the shape does not drift while it is being written.

1. **It answers, it does not enforce.** `authority(...)` returns an `Authority`; it never refuses a
   call, panics, or changes a code path. Phase 1 is a no-op and an enforcing predicate is not one.
   Enforcement arrives in Phase 3 as a different body behind the same name.
2. **It is a total function with a written-out table.** No `_ =>` arm. Twenty-four cells, every one
   spelled, so adding a `BlobKind` or a `Tier` is a compile error and Phase 6's weight-placement row
   cannot be added by accident.
3. **It is the only place the answer is written.** No site re-derives ownership from
   `accelerated()`, from `split`, or from a `matches!` on `BlobKind`. That is the property P3 tests
   and the property that makes the census a count rather than a sample.
4. **`Telemetry` returns exact answers in Phase 1.** `resident()` returns `bool`, not a probability.
   Widening it to `P(resident)` is Phase 4's first edit and is the change that stops results being
   byte-identical -- so it must not be smuggled in here, where the deliverable is that nothing moved.

## 4. Work items

### 4.1 `Tier` in `tier.rs`

```rust
pub enum Tier { Hbm, Ddr, Nvme }
```

Next to `TierSpec`, which is the same concept. `Hierarchy` gains `tier_of(kind) -> Tier`, resolving
`split` the way `on_accelerator` does today, and `pool(tier)` / `pool_mut(tier)` replacing
`home` / `home_mut`. `on_accelerator` becomes `self.tier_of(kind) == Tier::Hbm` at its nine sites.

This is the mechanical half and it is where byte-identity is won or lost, so it lands first and
alone: `tier_of` must agree with `on_accelerator` on every input, asserted by a test over the
product of `BlobKind::ALL` and `split`.

### 4.2 `own.rs` -- the predicate

```rust
pub enum Authority { Orchestrator, Engine }
pub enum Question { Capacity, Allocation }

pub fn authority(kind: BlobKind, tier: Tier, q: Question) -> Authority
```

Plus `Hierarchy::authority(kind, q)`, which resolves the tier first so callers on a node do not have
to.

The table, which is §1's table transcribed and is the artifact to review before any code is written:

| kind | tier | capacity | allocation |
|---|---|---|---|
| `KvBlock` | `Hbm` | Orchestrator (the partition) | **Engine** |
| `KvBlock` | `Ddr` | Orchestrator (the DDR quota) | **Engine** (offload connector) |
| `KvBlock` | `Nvme` | Orchestrator (the spill file) | **Engine** (§1.3) |
| `WeightShard` | `Hbm` | Orchestrator | **Engine** (once loaded; placement is Phase 6) |
| `WeightShard` | `Ddr` | Orchestrator | **Engine** |
| `WeightShard` | `Nvme` | Orchestrator | **Engine** |
| `Snapshot` | `Hbm` | Orchestrator | Orchestrator (unreachable; see below) |
| `Snapshot` | `Ddr` | Orchestrator | Orchestrator |
| `Snapshot` | `Nvme` | Orchestrator | Orchestrator |
| `ServiceHeap` | `Hbm` | Orchestrator | Orchestrator (unreachable) |
| `ServiceHeap` | `Ddr` | Orchestrator | Orchestrator |
| `ServiceHeap` | `Nvme` | Orchestrator | Orchestrator |

Two rows are unreachable today -- `tier_of` never returns `Hbm` for a host class -- and they are
still spelled rather than `unreachable!()`, because rule 2 wants the table total and because Phase
6's heterogeneous fleet is the phase that would make them reachable.

Tests assert each row of §1's *prose* table against this one, named for the row they encode, so the
doc and the code fail together rather than drifting apart.

### 4.3 `tele.rs` -- the `Telemetry` boundary

A read-only view the scheduler reaches engine state through. §8's "model agnosticism becomes
checkable" lists what the interface may contain; Phase 1 implements the entries today's scheduler
actually reads and leaves the rest absent rather than stubbed, with the full list in the type's doc
comment and the phase that fills each one named:

| entry | Phase 1 | later |
|---|---|---|
| `resident(kind, id) -> bool` | exact, from `is_hot` | Phase 4: `P(resident)` |
| `held(kind, id) -> bool` | exact, from `holds` | Phase 4: belief |
| `capacity/free/reclaimable(tier)` | exact | Phase 3: HBM becomes the partition |
| `resident_bytes(kind)` | exact | Phase 4: an estimate for engine classes |
| `marginal_price(tier)`, `regret_rate(kind)` | exact | Phase 3: engine-side becomes observed |
| hit / miss / eviction / refusal counts | exact | Phase 4: the `Metrics { interval }` channel |
| queue depth, batch occupancy | from `Engine` | Phase 4: sampled |
| load and unload cost per model, context window | absent | Phase 6 |
| directive channel | absent | Phase 5 |
| cancellation | absent | with the data path (§8) |

`machine.rs`'s `believes_resident` and `believes_held` read through it. `apply_chain` and
`apply_deps` do not, and gain `ground_truth_holds` per §1.4.

**Borrow risk, and the fallback.** `Telemetry<'a>` borrowing `&'a Hierarchy` and `&'a Engine` out of
a `Machine` that is `&mut self` on the serving path may not satisfy the borrow checker without
splitting fields. If it does not, the fallback is to make `Telemetry` an `impl Machine` block in
`tele.rs` rather than a struct: same discipline, same single place to change in Phase 4, no
lifetime. Take the fallback early rather than restructuring `Machine` for it -- restructuring
`Machine` is how a no-op phase stops being one.

### 4.4 The census

A `census` feature, off by default, that costs nothing when it is off:

```rust
#[cfg_attr(feature = "census", deprecated(note = "assumes allocation authority over engine state"))]
fn admit_engine(&mut self, id: BlobId, meta: BlobMeta) -> Admission
```

on the authority-split entry points from §1.5 -- `admit_engine`, the engine-side `anticipate`,
`touch`, `remove`, `demote`, `drain_all` -- and on `Quota`'s per-class accessors for engine classes
per §1.6.

Then:

```
cargo build --features census 2>&1 | grep -c 'use of deprecated'
```

is the number, and `cargo build` -- the quality gate -- stays warning-free, which is why this is a
`cfg_attr` and not a bare `deprecated`. Nothing is actually deprecated; the attribute is being used
as the only per-use-site lint the compiler offers without a proc macro. Say so in the feature's doc
comment, because a reader who finds `deprecated` on live code deserves an explanation.

**What this counts, stated precisely, because the obvious reading is wrong.** An earlier draft of
this section said "internal forwarders carry `#[allow(deprecated)]` so a two-hop call counts once".
That instruction is incoherent against how the lint actually behaves, and following it would have
zeroed the census. `#[deprecated]` fires at the *direct textual call site* of the deprecated item
and does not propagate to callers of callers -- so a chain `materialise -> admit_hot ->
admit_engine` already warns exactly once, at the one line inside `admit_hot`, with no `allow`
needed anywhere. Adding `#[allow(deprecated)]` to the dispatchers would have suppressed that single
line and left nothing to count, since by design no code outside a dispatcher names an `_engine`
function at all. **So the number is a count of authority-split entry points, not of call sites into
them**, and it moves only when such an entry point is added or removed. That is still the right
quantity for sizing Phase 3 -- each one is a body Phase 3 replaces -- but it is not the quantity
§9's phrase "call sites" suggests, and P2 in §2 was written against the wrong one.

**A second number, no longer optional.** Per-entry-point counters give the *dynamic* census -- how
many decisions on engine-owned state a run actually takes. The static count says how much code
changes; the dynamic count says how much of the simulator's behaviour rests on the disclaimed
authority. One counter per marked entry point, reported as a table by `polyphonic ownership`.

**The trap this walked into twice, recorded because it will recur in Phase 3.** A census is only
as complete as the set of entry points someone thought to split, and both times the gap was found
by reading the call graph rather than by anything failing. First, a single counter on
`admit_engine` reported 20,143 `KvBlock` operations when the true figure was an order of magnitude
higher. Then, with five entry points split, `materialise` turned out to drop superseded copies
inline (`ddr.remove`, `nvme.remove`) instead of through `forget_cold` -- so every offload and spill
*hit*, the hot path, was uncounted. The two paths now report separately, and the split is the
clearest single picture of the miss: 2,474 removals on the counted path against 59,904 on the one
that was not. In the
same pass `demote_body` was spilling DDR victims through `spill` directly, bypassing its own
dispatcher and leaving the entire eviction cascade -- 86,753 operations, as large as admission
itself -- with no attribution at all, in violation of the rule `demote`'s own doc comment states.
**Neither gap was detectable from inside the census.** The static count looked healthy at 5 and
then 9; the dynamic table showed plausible non-zero numbers in every column. What exposed them was
asking which code paths touch engine state and checking each against the dispatcher list.

## 5. Verification

- **Byte-identity.** Capture stdout at `HEAD` before the change, re-run after, `diff` with zero
  tolerance: `residency`, `flows`, `placement` (split and unified memory), `volatility`, each at a
  reduced `--ops` for turnaround and at a second seed. These four are the whole reproducible set --
  checked by running each twice and diffing, not assumed. `distributed`, `code-review` and
  `data-path` all call `boundary::measure` and print its live host timing inline with the served
  results (`grpc = 47.8 us ... (MEASURED on this host)`), so two back-to-back runs of any of them
  already differ before this phase touches a line, the same as `boundary`, `calibrate` and
  `topology`. Originally this section named the boundary-measuring three as part of the byte-identity
  set; running the check against itself twice showed they cannot be, which is worth recording since
  it means "byte-identical over a set chosen after the fact" was itself getting it wrong here. Those
  three still get a smoke run before and after -- same node/served/refused counts, same arm labels,
  timings free to move -- to catch a structural break the deterministic four would not exercise
  (`code-review`'s single-engine host, `distributed`'s gossip arm).
- `cargo fmt --check` and `cargo clippy --all-targets --all-features` clean, as today.

## 6. Risks

1. **Scope creep into Phase 3.** The whole phase is one refactor away from "while we are here, make
   `admit_engine` an LRU". That is the correction, it is not a no-op, and it would land without
   Phase 2's oracle to measure it against. The split in §1.5 exists to make the temptation explicit
   and then refuse it.
2. **The borrow checker forces a `Machine` restructure** (§4.3). Mitigated by taking the `impl`
   fallback rather than the struct.
3. **The census over- or under-counts.** Over-counting is handled by the authority split and
   `#[allow(deprecated)]` on forwarders. Under-counting is real and unfixed: a site generic over
   kind -- `access()` walks a chain of mixed classes -- counts once, not once per class it may carry.
   That is arguably the correct answer, since it is one place Phase 3 must change, but it means the
   number is a count of *sites*, not of *decisions*, and the two should not be quoted
   interchangeably. The optional dynamic count in §4.4 is the other half of that pair.
4. **§1.3's NVMe choice is a judgement, not a derivation.** Its effect on the census is named in
   §1.3 so a reviewer can price the alternative without re-reading the code.
5. **`deprecated` as a census instrument is a misuse of the attribute.** It is the only per-use-site
   lint available without a proc macro, it is feature-gated off by default, and the alternative --
   a `#[cfg(feature = "census")]` that deletes the accessor and counts compile errors -- cascades
   through type inference and produces a count of error *messages* rather than sites. Documented
   rather than avoided.
6. **Byte-identity is a weak test of a type refactor.** It catches changed arithmetic; it does not
   catch a wrong cell in the §4.2 table, since Phase 1 never branches on the answer. The table is
   tested against §1's prose and reviewed as prose, and that is the only check it gets until Phase 3
   branches on it. Worth knowing before Phase 3 finds a wrong cell the expensive way.

## 7. Out of scope

- **Anything that changes a result.** Phase 3 is the correction; Phase 2 is the apparatus that makes
  it measurable. Phase 1 precedes both and must move no number.
- **`P(resident)`, lossy telemetry, ZMQ ingestion, sequence gaps, divergence.** Phase 4. `Telemetry`
  is shaped to receive them; it does not contain them.
- **The `RequestView` half of §3.1** -- making `Request`'s ground-truth fields private and giving the
  scheduler an observables view. That is the `req.tokens` cheat, a *workload* ground-truth leak
  rather than an engine-state one, and closing it changes the placement score. Phase 4.
- **Retention directives, `retain_until`, `evict_first`.** Phase 5.
- **Partition sizing as a decision, tenancy, weights as orchestration.** Phase 6. The `Capacity`
  arm of the predicate exists for them and is answered uniformly until they arrive.
- **Removing `accelerated()`.** It stays as a tier predicate, which is what P3 predicts it always
  was.
